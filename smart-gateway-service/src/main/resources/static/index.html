System Architecture

How Gatekeeper Operates

A decoupled Data Plane and Control Plane architecture designed for sub-millisecond routing and zero single-point-of-failure operation.

STEP 01

Client Ingress

Clients submit HTTP requests to Gatekeeper. The gateway generates an X-Correlation-ID, validates path matches using Spring's PathPatternParser, and enforces allowed HTTP methods.

STEP 02

Policy Enforcement

Redis evaluates per-tenant rate limit token buckets and verifies idempotency keys for POST requests. Malicious or excess requests are stopped with HTTP 429 or HTTP 409 before reaching upstreams.

STEP 03

Security & Rewriting

Hop-by-hop headers (Connection, Host, Transfer-Encoding) and spoofed forwarding headers are stripped. Path prefixes are rewritten to match backend expectations.

STEP 04

Upstream Dispatch

Java 21's native bounded HttpClient streams payloads up to 4 MiB to allowed origins, strictly enforcing connection and response timeouts without following unverified redirects.

🛡️

Zero-Trust Header Sanitation

Blocks header injection and request smuggling attacks by removing sensitive transport and spoofed proxy headers before passing requests to private internal backends.

⚡

Kafka Event Synchronization

When operators create or update routes in the API Management Control Plane, JSON change notifications are published over Kafka to trigger instant route reloading without downtime.

🔒

Role-Based Multi-Tenancy

Strict isolation between PLATFORM_ADMIN and TENANT_ADMIN roles. Tenant administrators can only manage routes bound strictly to their assigned organization prefix.
